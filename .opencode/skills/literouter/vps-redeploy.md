# VPS Redeploy: dev fix → production

> Load this file when the task is "deploy / push / sync / ship the fix to the VPS",
> "the VPS is running old code", or "restart the gateway so it picks up the change".
> It is **not** needed for local development or for reading code.

## ⛔ The one rule that matters

**WSL is the single golden truth.** Never `scp` a patch to the VPS, never `ssh` in and
edit a source file, never hand-patch production config. Every production change goes:

```
dev (WSL)  →  git commit  →  git push  →  VPS pull  →  restart  →  health probe
```

A hand-edit on the VPS survives only until the next `git pull`, which silently reverts
it. This exact failure already happened: the Zen `403 FreeTierError` fix was applied by
editing `config/providers.json` on the VPS, and `scripts/gateway/start.sh:66` regenerated
the bad value at the next boot.

Two flows exist. Pick by what changed:

| Flow | Use when | Command |
| :--- | :--- | :--- |
| **Full sync** (golden truth) | Anything touching `.env`, `.env.local`, `config/`, or providers | `bash scripts/sync/sync_literouter_to_vps.sh` |
| **Code-only pull** | Only `src/`, `tests/`, docs, or scripts changed | `bash scripts/sync/vps_git_pull.sh --restart` |

## Step-by-step: code-only redeploy

`scripts/sync/vps_git_pull.sh` is **gitignored** (see `.gitignore`), so it is a
per-operator local script. If it is missing on this machine, recreate it from this
section — it is ~140 lines and its behaviour is specified below.

1. **Commit and push from dev.** Nothing reaches the VPS otherwise.
   ```bash
   cd ~/arthityap/literouter
   git add -A && git commit -m "..."
   git push origin main
   ```
2. **Pull the code onto the VPS** (does *not* restart):
   ```bash
   bash scripts/sync/vps_git_pull.sh --dry-run   # inspect the delta first
   bash scripts/sync/vps_git_pull.sh             # pull, install deps, typecheck
   bash scripts/sync/vps_git_pull.sh --restart   # pull + restart + health gate
   ```
3. **Verify.** The script refuses to restart if `bun run typecheck` fails on the VPS, and
   aborts if `/health` does not return `{"status":"healthy"}` within 15 s.

### Required behaviour of `vps_git_pull.sh`

Reproduce these properties if rewriting it — each one exists because its absence caused
a real failure:

- **Refuse on modified *tracked* files only.** Use
  `git status --porcelain --untracked-files=no -- ':!config/providers.json'`.
  Untracked paths (`LOCK`, `config/location.json.bak.*`, `oldgen/`) are always present
  on the VPS and must NOT block a deploy; git leaves them alone. Checking without
  `--untracked-files=no` makes the script permanently refuse to run.
- **Stash `config/providers.json` around the pull.** It is regenerated by
  `start.sh` on every boot, so its dirty state is expected; a rebase must not trip on it.
- **Never touch `.env` / `.env.local`.** Secrets are WSL-owned. If a change requires them,
  use the full sync script instead.
- **Typecheck on the VPS before restarting.** A broken commit must not reach production.
- **Never restart unless `--restart`.** The gateway serves live traffic on `:7766`;
  an unsolicited restart is an outage. Without the flag, print a warning that the VPS
  still serves the old code.

## Full sync: what it does

`scripts/sync/sync_literouter_to_vps.sh` (tracked in git) runs, in order: source
preconditions → SSH check → **remote `.env*` backup** to `~/backups/literouter_sync/` →
`git fetch` + `git checkout -- config/providers.json` + `git pull --rebase` → `scp` of
`.env.local`/`.env` with a **sha256 equality check** → tmux env purge → gateway stop and
start → `/health` gate (15 × 1 s) → key-pool inspection. Flags: `--skip-git`,
`--restart-only`.

## After deploying a `src/` change

The new code only takes effect once the gateway process restarts. Confirm the running
process actually has it:

```bash
ssh vps466a 'cd ~/services/literouter && git rev-parse --short HEAD'
curl -s http://192.168.50.10:7766/health
```

## Reading failures that only appear in production

- Gateway stdout is `~/services/literouter/logs/gateway.log` on the VPS (~400 k lines,
  timestamps are `MM-DD-HH:MM:SS:ms`, **local time**, not ISO).
- Per-request traces (status, duration, provider, model) are in
  `~/services/literouter/logs/traces.db`. No `sqlite3` binary on the VPS — query with
  `~/.bun/bin/bun` + `bun:sqlite`, or copy the file down.
- **A streamed request that produced an `event: error` frame still records as HTTP 200.**
  `createCutoffResilientStream` commits the response before the body is consumed. Since
  the 2026-10-05 fix these now emit a `[STREAM <req_id>] In-band upstream error [...]`
  line — to count in-band failures:
  ```bash
  grep -c "In-band upstream error" ~/services/literouter/logs/gateway.log
  ```
  Before that fix the failure was completely invisible (measured: 60 of ~3,400
  streaming requests over 5 hours, ~1.8%).
- When correlating an omp/client failure to a gateway request, match on
  `\[(SERVED|TTFT|USAGE|ROTATE) (req_[a-z0-9]+)\]`. The `💬 … Tokens:` usage line has no
  `[req_id]` bracket, so splitting on a bare id leaks the previous request's id into the
  next line and silently corrupts every per-request count.

## Never

- Never restart the production gateway without explicit user approval. "YOLO mode"
  covers the local sandbox only.
- Never `git push` or `bd dolt push` without explicit authorisation — default is
  conservative: report `git status` and the proposed commands.
- Never edit `.env` / `.env.local` content, and never let an automated tool redact them.
  Replacing a key with `<REDACTED>` drops the whole pool at boot and the gateway will not
  start.
